# 18 · 本地通知（生成完成，深链回会话）

> G2 逐屏规格。基准：通知横幅按 iPhone 三档宽度校验（393 为主，附 320/430 的截断口径）。
> 要点源：`inventory.md` 行 18。**不是 App 内屏幕**：交付物 = 通知样式 + 路由契约 + 授权/兜底态。
> 前提：**NEEDS-7 未就绪**（远程推送 token 注册端点缺）→ v1.0 用**本地通知兜底**（PRD 4.2）。
> 通用态规范源：`17-state-gallery.md`。

## 1. 屏与上下文

- **形态**：`UNUserNotificationCenter` **本地**通知（App 被杀/退后台也能显示的前提见 §7「调度」）。
  非 Push、非 App 内横幅、**不是**实时服务端消息（NEEDS-7 未解锁，PRD 4.4「远程推送不做」）。
- **入口**：通知点击 = 唯一的本「屏」交互 → 深链路由到 **09 会话详情**。
- **返回行为**：从通知进入的栈 = `01 → 08 → 09`（**不**是裸 09，保证返回有路）；
  App 已在 09 同一会话时 → 不重开，仅滚动到目标卡并把未读点清掉（08 §3.A 联动）。
- **互链**：09（目标）、08（红点与排序回收）、15（授权态回显与跳系统设置）、12c（成果计数，
  受契约限制不渲染）。
- **可关性**：App 内不自建开关（15 §3.E 钉死：只回显系统授权 + 跳系统设置）。

## 2. 布局（通知自身 + 深链后的表现）

```
锁屏 / 横幅（393 宽）
┌───────────────────────────────────────────┐
│ ● Cova                            现在 ⌄   │  A 系统行（App 名 + 时间）
│ 你的歌做好了                                │  B 标题（固定串）
│ 「夏夜回声」「晚风站台」两个版本都完成了     │  C 正文（双候选名）
╰───────────────────────────────────────────╯
     │ 下滑/点按 → 深链
     ▼
路由：session-detail
  sessionId    : String   （必需，来自 GenerationJob.sessionId）
  jobId        : String   （必需，通知 userInfo 携带）
  planCardId   : String?  （可选：定位并展开该计划卡）
  candidateId  : String?  （可选：滚动到该候选卡）
  source       : "local-notification"  （埋点/防重复消费，非后端字段）
     ▼
09 会话详情：A 导航条 → 目标候选卡一次性高亮
   （2pt color.accent 描边 + duration.slow 淡出；Reduce Motion 下一帧显一帧消）
```

App 图标角标：+1（进入 09 该会话即清零，见 §8）。

## 3. 区块规格（文案与视觉）

- **A 系统行**：App 名取 `CFBundleDisplayName`（`Cova`，Config/Info.plist 已钉）；
  声音 = 系统默认（v1.0 **不自定义**声音文件，避免随包资源与合规噪声）；
  横幅样式 = 系统默认（`banner` + `list`，锁屏可见）
- **B 标题**：固定串「你的歌做好了」（`inventory.md` 行 18 钉死），**不**随内容变化
  （稳定串便于用户形成条件反射，也避免标题里出现歌名的截断歧义）
- **C 正文**：`「<候选 1>」「<候选 2>」两个版本都完成了`（双候选名，见 §8 截断与单候选规则）
  - 名源 `GenerationCandidateDto.title`（契约字段）；两名为空时回落「两个版本都完成了」
  - **禁止**出现：音频 URL、签名 URL、token、`co 币`、余额、价格、任何「点击查看/领取」类诱导词
    （AGENTS 硬边界 3 + D12）
- **D 图片附件**：v1.0 **不加**封面附件（`NotificationServiceExtension` / attachment 需
  额外 target 与随包逻辑，且 `coverUrl` 可能是授权地址 → 不做）。登记「待裁决 2」
- **交互控件**：v1.0 **不加**通知动作按钮（「试听 / 收藏」需 category + 权限 + 后台播放能力，
  且收藏要带 `mediaReferenceId` 写操作 → 属 M2 之后的增强）。见「待裁决 3」
- **高亮表现（09 内）**：目标卡 2pt `color.accent` 描边（TG-04），
  `motion.duration.slow` + `motion.curve` 淡出；滚动定位用系统 `scrollTo`，不加自定义弹跳

## 4. 状态变体

- **加载**：不适用（通知无加载态）。深链进入 09 的加载态由 09 §4 承接
- **空态**：不适用
- **错误 / 兜底（本节 = 本屏的核心）**：
  | 情形 | 表现 |
  |---|---|
  | 授权为 `denied`（用户关了通知） | **不**在 App 内反复索权。生成完成后：回前台时由 08 行左侧的
    「完成指示点」（`color.accent`，TG-18）+ 09 会话内候选卡组终态条承担「做好了」的告知；
    15 设置 E 行右值显「已关闭」；**不**弹自建 Dialog 催开权限 |
  | 授权为 `notDetermined` | 首次进入**需要它的那一刻**才索权：用户在 09 点「开始制作」成功后
    （有明确收益时）弹系统授权；拒绝即落上行 |
  | 授权 granted 但 App 被系统回收/后台任务未跑完 → 通知未发 | 回前台对账：若 job 已终态且
    未发过通知 → **不发**迟到的通知（避免「昨天做好的歌今天弹」），改为 08 完成指示点
    + 进入 09 后正常呈现终态。幂等：同一 `jobId` 只允许调度一次通知（本地已发记录，owner 绑定） |
  | 深链目标已不存在（会话被删/404） | 09 整屏错误态「这个会话已经不在了」+ 返回钮（08 §8 同文案），
    **不**弹额外提示 |
  | 深链 `sessionId` 缺失/畸形（伪造或旧版本） | 回落 01，**不**尝试拼路由（防越权进他人会话）；
    不写日志明文（AGENTS 硬边界 3） |
  | 离线（无网）时点击通知 | 进 09 → 走 09 §4 离线态（缓存消息 + 离线条）；
    若本地无该会话缓存 → 整屏「离线：创作需要联网」+「重试」 |
  | 同一轮多 job 并发完成 | 合并为**一条**通知（取最后完成的 `jobId`，正文仍列两个候选名）；
    去抖窗口 = `motion.duration.page` 的整数倍由实现定，**不**做成多条轰炸 |
- **Reduce Motion**：横幅出现由系统控制（App 不可干预）；09 内高亮淡出退化为一帧显、一帧消；
  角标数字变化无动画

## 5. 深浅双主题差异

- 通知外观完全由系统主题呈现，App 侧**无**可定制色值（这是好事：不存在主题硬编码风险）
- 唯一 App 侧差异 = 深链后的高亮描边 `color.accent`（双主题同值）与 08 完成指示点同 token
- 09 的会话内表现遵循 09 §5，不新增本屏专属值

## 6. 可访问性

- 通知朗读由系统 VoiceOver 处理：标题 + 正文按顺序朗读，因此**正文必须自带完整语义**
  （不能依赖「点击查看」这种屏幕外动作补齐信息）
- 深链进入 09 后：VoiceOver 焦点落在**目标候选卡**（不是屏幕顶部），标签
  「版本 N，<标题>，<状态>，来自通知」；未读指示点在 08 的行标签里体现
  「有完成的新版本，」前缀（色点不是唯一通道）
- 角标（badge）对辅助功能无语义承载 → 不作为任何信息的唯一表达
- 触控/ Dynamic Type：本屏无自有 UI；09 内表现遵循 09 §7

## 7. 数据契约与调度

| 用途 | 来源 | 说明 |
|---|---|---|
| 触发判定 | `GET /api/find-my-song/generation-jobs?id=` 的 `job.status`（6 态）+ `metadata.candidates[]` | **双 Demo 终态硬规则（D7）**：前两候选都 settled 才触发；`succeeded` 但候选未双 settled → **不**通知（否则「做好了」是假的） |
| 标题里的歌名 | `GenerationCandidateDto.title` | 契约字段 |
| 深链参数 | `job.sessionId`、`job.id`、候选 `id`、计划卡 `planCardId` | 全部为契约已有 id，不含用户隐私串 |
| 完整音频交付 | 计划卡 `status = delivery_preparing → …`（09 §9） | v1.0 **不**为「完整音频就绪」再发第二条通知（噪声），见「待裁决 4」 |
| 授权 | `UNUserNotificationCenter` 系统授权态 | 15 §3.E 回显；NEEDS-7 未解锁 → 本地通知为唯一手段 |

- **调度口径（必须写清，否则退后台就永远不通知）**：
  1. 前台：正常消费 SSE/轮询 → 命中终态即调度（延迟 0）；
  2. 退后台：`UIBackgroundModes` 只声明 `audio`（Info.plist）→ **不能**保证后台仍在轮询。
     v1.0 采用「**发起时预约一条延迟本地通知**」：`plans/start` 成功后，按
     `job` 的常规耗时上限预约（api-contracts §4：轮询上限约 30 分钟）一条
     `+N 分钟` 的本地通知，`userInfo` 带 `sessionId/jobId/planCardId/candidateId 占位`；
     命中真实终态时 `removePendingNotificationRequests` 撤掉预约并发改为即时内容通知；
     App 被杀 → 预约通知仍会响（正文只能给「两个版本应该好了，去 Cova 听」的**未定名**措辞，
     因为它拿不到候选名）→ **待裁决 1**（措辞二选一）
  3. **禁止**在通知内容里放任何 URL（含 `covalink.cn` 链接文本），只放 id 型 userInfo
- **不得发明**：后端无「通知注册/推送」端点（NEEDS-7 缺）、无 `notificationId`、无「已读回执」字段。
  已发/未发状态是**纯本地**事实（owner 绑定，D9），换设备即重置——验收时按此口径判，不当缺陷
- **深链承载方式（工程缺口）**：`Config/Info.plist` **无** `CFBundleURLTypes`、无
  associated domains → 需二选一（属工程配置变更，非设计能定）：
  ① 自定义 scheme `cova://session/<sessionId>?job=<jobId>&plan=<planCardId>&candidate=<id>`；
  ② Universal Link（需域名 + `apple-app-site-association`，涉服务器 → 越出本仓边界，需用户批准）。
  **路由参数结构以上表为准**，两种承载都不改语义 → 见「待裁决 5」
- **可空规则**：`sessionId` 缺 → 不深链（回落 01）；`planCardId/candidateId` 缺 → 进 09 但不定位、
  不高亮；`title` 空 → 正文回落通用句

## 8. 边界与文案

- **截断（通知正文按三档宽度校验）**：
  - 393 宽：正文可见约 2 行；单候选名 >8 字 → 该名片段截断为 8 字 + `…`，**两个名合计 ≤20 字**，
    超出时优先保第一个名完整
  - 320 宽（小屏/放大字号）：单名 ≤6 字；430 宽：单名 ≤10 字
  - 单候选（另一失败）：正文改「「<候选 1>」做好了，另一版没完成」；两候选皆 failed：
    「这次两个版本都没做成」——**失败也要通知**（否则用户白等），但**不**用红色/感叹号（系统通知无此语义）
- **文案清单（固定串，禁改）**：
  - 标题：`你的歌做好了`
  - 正文（双就绪）：`「%@」「%@」两个版本都完成了`
  - 正文（一就绪）：`「%@」做好了，另一版没完成`
  - 正文（双失败）：`这次两个版本都没做成`
  - 正文（预约/未定名）：`两个版本应该好了，去 Cova 听`（待裁决 1）
  - 会话内高亮不产生新文案
- **零余额 / D12**：通知与正文不得出现 co 币、余额、充值、价格；`job.costCredits` **不**入通知
- **极值**：同一会话连续多轮制作 → 每轮各一条（按 `jobId` 去重），不合并跨轮；
  待处理通知 >4 条时系统自会折叠，App 侧不额外限制（但已发记录仍逐条幂等）
- **并发冲突**：
  - 通知调度与用户主动进 09 同时发生 → 已进入该会话则**取消**待发通知并清角标
  - 登出（15 §3.H）时：撤销所有 pending 通知请求 + 清角标 + 清「已发记录」（D8 清 owner 数据）
  - 深链解析与冷启动时序：App 冷启由通知进入时，**先**完成会话恢复（`restoreSession`）再消费路由，
    否则会带着错误身份进 09（D5 串号风险）

## 9. 验收判据

- [ ] 双候选**都** settled 才出现「两个版本都完成了」；一 ready 一 pending 时**不发**通知（D7 取证项）
- [ ] 两候选皆失败时仍发一条，且正文用双失败串、无诱导词、无 URL、无金额（合规扫描）
- [ ] 通知 `userInfo` 与日志中检索不到 `audioUrl` / `audioDownloadUrl` / token / 签名地址
- [ ] 深链四种情形逐一验证：正常进 09 并定位高亮 / 会话 404 → 09 错误态 / `sessionId` 缺失 → 回落 01 /
      离线且无缓存 → 离线条 + 重试
- [ ] 冷启动从通知进入时，恢复会话**先于**路由（不得出现「进 09 后因 401 被踢回登录」的错序）
- [ ] 同一 `jobId` 只收到一条通知（重复轮询/重进不重复弹）；进入该会话后角标清零、08 指示点消失
- [ ] `denied` 态下 App 内不重复索权、无自建开关，15 设置 E 行右值为「已关闭」，
      完成信息改由 08 指示点 + 09 终态条承担
- [ ] 三档屏宽（320/393/430）下正文按 §8 截断规则，不出现系统级中间截断（`…` 由 App 侧决定）
- [ ] 登出后无 pending 通知残留（生命周期攻击项：通知残留）

## 待裁决

1. **预约通知的措辞**：App 被杀后只能发「未定名」通知（拿不到候选名）。
   选项 A = 用「两个版本应该好了，去 Cova 听」；选项 B = 不发预约通知，仅在回前台时告知。
   **建议 A**（承诺感更强），但「应该好了」是不确定表述 → **待用户裁决**。
2. **是否加封面附件**（`coverUrl`）：需要先确认该地址是公开还是授权型；授权型入通知 = 凭证外泄面，
   与 AGENTS 硬边界 3 冲突 → 本规格不做。
3. **通知动作按钮**（试听/收藏）：收藏是写操作、试听需后台音频能力，均属 M2 之后的增强 → v1.0 不做。
4. **「完整音频就绪」是否第二条通知**：`delivery_preparing` 完成时再发一条会形成同轮双通知。
   本规格：**不发第二条**，09 内 I 进度条终态承载。若产品要，需重开文案与去重设计。
5. **深链承载**：`cova://` 自定义 scheme（只改本仓 `Config/Info.plist`）vs Universal Link
   （需服务器侧文件，越出本仓边界）。**建议 scheme 起步**，G4 前评估 Universal Link。
   属工程配置变更，**需用户批准**（本任务不改 `Config/`）。
6. **失败也通知**：本规格选「是」（用户白等的体验更差）。若产品认为「失败不该打扰」，
   则只发成功通知，失败靠 08/09 承接 → **待裁决**。
