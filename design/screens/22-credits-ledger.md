## 6. 可访问性

- **朗读顺序**：「co 币明细，标题」→ 返回 →（B 存在时）「6 条变动」→ 列表
  「变动记录，6 项」→ 每行**单元素**复合标签：
  「AI 音乐生成，扣 20 co，余额 108，2 小时前〔，任务 按钮〕」
  - `amount` 朗读必须带方向词（「扣」「加」），**不**朗读符号名（「减号」）；
    不可判方向时只朗读数字与单位（「20 co」），不朗读「变动」之类的猜测词。
  - 「余额 108」紧接金额，让用户先知道结果再看时间（顺序即心智）。
  - 「任务」钮在行标签末尾出现，**仅当它真实存在**；不存在时序列里也不许有占位元素。
- E 尾部行作为列表**之后**的独立静态元素朗读（「这里只有最近 100 条变动」）——
  它是本屏最重要的一句事实，不得因装饰性考虑而设 `accessibilityHidden`。
- **Dynamic Type**：AX 档下——第一行标签与金额仍同行（金额不被挤出，标签 1 行截断）；
  第二行的时间与「余额 %d」上下堆叠；「任务」钮恒换到第三行满宽。
- **触控目标 ≥44pt**：返回 / 每枚「任务」钮 / 空态主 CTA / 重试钮。（行本身非交互，不设目标。）

## 7. 数据契约

| 用途 | 端点 | 字段与说明 |
|---|---|---|
| 明细 | `GET /api/me/credits/ledger?limit=100` | 响应 `{entries}`（契约 §4.6）。每条 `{id, type, amount, balanceAfter, reason, reasonLabel, jobId, createdAt}`；`Cache-Control` 未记录 ⇒ 不假设可缓存 |
| 任务关联 | 同响应 `jobId` | 契约 §4.6：「由服务端从 `metadata.jobId` 解出」；**§7 #38 复测：两支有值、`studio_create_generation` 一支恒 null** ⇒ 客户端按可选建模，逐行判 |
| 跳转目标 | `GET /api/studio/create/works?id=<jobId>` | 由 20 的任务定位形态消费（契约 §4.4 明写纯 jobId 返回该 job 全部行）；本屏**不**直接调它 |
| 余额现值 | **不调** `GET /api/auth/me` | 顶部不重复余额（「待裁决 1」）；每行的 `balanceAfter` 已是过程事实，再拉一个现值只会造出「两个余额打架」的观感 |

- **「只能看最近 100 条」的诚实边界（本屏的核心判据，四条硬规则）**：
  `limit≤100` 是上限，而响应 `{entries}` **既无 `cursor`/`nextCursor`，也无 `total`** ⇒
  ① 请求侧：本屏恒发 `limit=100` 且**只发一次**（不 `offset`、不 `page`、不 `before`、不 `since` ——
  都不在契约里）；
   本屏的措辞据此成为**长期口径**而非临时降级（§4.7 的实测卡里就没有游标这件事）。
  ② 呈现侧：`entries.count == 100` 时尾部行必须说「这里只有最近 100 条变动」——
  它是**服务端边界**的陈述，不是「加载失败」的道歉，因此用 `color.muted` 中性色、不配告警符号；
  ③ 禁止假分页：**不得**把 100 条本地切成 10 屏 × 10 条再挂「上滑加载更早」（那是在把
 手册 §7 #38 之外的第二个真实边界藏起来，用户会一直往下滑并以为后面还有）；
  ④ 禁止把边界伪装成穷尽：「已显示全部」只在 `entries.count < 100` 时出现。
  ⇒ 这一条与 `17-state-gallery.md` §10 的「统一措辞：已显示全部」构成**一处偏差**（该措辞预设了
  「到底 = 全量」，而本屏的到底只是「取满了」），已登记在 `inventory.md` 偏差表，
  并在 §E 里给出第二语义串。「更早的变动去哪里看」**不承诺**（无端点、仓内无「官网可查全量」的
  明文依据）⇒ 「待答（2）」。
- **`jobId` → 「任务」关联（A9 的现场）**：`jobId` 非空 ⇒ 渲染 D 钮，点击 → 20 的 `?job=` 形态；
  `jobId` 为 null / 缺键 / 空串 ⇒ **不渲染**（用户要求写死的这一条，落成机械判据见 §9）。
  **今天哪些行会有「任务」钮（手册 §7 #38 已复测，结论是后端缺陷而非「字段晚于旧账」）**：
  同一份响应 7 条里，`cova_one_step_generation` 与 `library_download_checkout` **带 jobId**
  ⇒ 这两类行**会**出现「任务」钮；而 **`studio_create_generation` 这一支恒
  `jobId=null` / `unlinked=true`**（2026-09-26 新账实测，-100、bal 19415）⇒ 那一类行**不会**有钮。
  ⇒ A9 的「`studio_create_generation` 行 `jobId` 非空」今天不可能达（§7 #38 已改判**待修**）。
  实现不得为让判据好看而用 `id`/`reason` 拼一个假关联，也不得把「任务」钮常驻再靠点击后报错。
  ⚠️ 另记一条：§4.6 的字段清单里**没有** `unlinked` 这个键，但它在 §7 #38 的实测里出现了
  ⇒ 本屏**不建模、不渲染**它（无契约即不做），只把它作为「待答（9）」问一句：
  这个键是不是给客户端用的「本条无法跳转」判别位？若是，请进 §4.6 并给语义。
- **`±` 符号的判定（字段口径未闭合 ⇒ 保守施工）**：`amount` 与 `type` 的符号约定**未文档化**
  （契约 §4.6 只给了键名，`type` 的取值集合站内无一处列举）。本规格钉：
  ① `amount` 为**带符号**数值（负值存在）⇒ 直接按符号渲染 `+` / `−`；
  ② `amount` 恒为正数且 `type` 命中客户端已知的方向枚举 ⇒ 按 `type` 判方向；
  ③ 两者都判不出 ⇒ **符号位不渲染**，只显示数字与「co」。
  **禁止**用「`balanceAfter` 与上一条比较」反推方向（他端并发变动会把推断做错，
  且那等于把服务端账目交给客户端重算）。⇒ 「**待答（1）**」。
- **`reasonLabel` 是唯一文案源（契约 §4.7 明令，本条覆盖 §4.6 的旧写法）**：
  ① `reasonLabel` 非空 ⇒ **照原值上屏**（服务端已给中文，iOS 不翻译、不改写、不「统一术语」、
  **不再自己映射一遍**）；
  ② 早先版本在这里写了「客户端按 `reason` 查本地映射」的兜底表，**已撤销**：§4.7 实测
  服务端映射表与真实 reason 不同步，24 个在写的 reason 里 **13 个落到「其他变动」**
  （含补充制作的 `media_extra`、`cova_ai_agent_generation`、灵感商店一族、
  `iap_credits_purchase`、admin 三件）⇒ iOS 再映射一遍就是**第二套口径**，
  那是本仓「min-2 缺陷族」的标准成因。旧条目备查：
  （§4.6 给的条目：`studio_create_generation`=AI 音乐生成、退款一族、`daily_checkin`=每日签到；
  注意 §4.7 已更正：**不存在** `generation_refund` 这个 reason，真实值是
  `cova_one_step_generation_refund` / `cova_ai_agent_generation_refund`。）
  ③ **客户端唯一的兜底**：`reasonLabel` 缺失或空串 ⇒ 「其他变动」。
  这一句**不是映射**（没有任何 `reason` 参与判定），且与 §4.7 记录的服务端兜底桶**同串**；
  ④ **绝不**把英文码上屏：`reason` 只用于分支判断（例如「这一条能不能跳作品」），
  **永不上屏**（17 §10 禁技术词 + 手册 §6 A15 术语口径）；
  ⑤ `type` 字段同样**不上屏**（取值集合未文档化，§7「±」条）。
  ⇒ 「待答（3）」要的是**服务端补映射表**，不是 iOS 补代码。
- **异常值与可空规则**：`balanceAfter` 为负 / 异常大 ⇒ 该行的「余额 %d」位显 `--`
  （11 §7 同规则：不显示可疑数字；`--` 的色档 = TG-29）；`amount` 缺失 ⇒ 金额位整段不渲染
  （该行仍保留，明细行不能因缺字段消失）；`createdAt` 缺失 ⇒ 时间位不渲染（不显示「—」噪声）；
  `id` 缺失 ⇒ 该行**不渲染**（无稳定标识会造成重复行与误删风险，12a/12b/16 一致：
  解码不出稳定 id 的行宁可不上）。
- **排序**：以后端返回顺序为准，客户端**不重排** —— 契约 §4.7 记的是**固定
  `createdAt DESC, id DESC`**（同秒的账由 `id` 定序 ⇒ 天然稳定，12a §7 同判据）。
  本屏因此**不**提供本地排序控件、也**不**做「按金额/按类型」筛选（§4.7：请求侧只有 `limit`
  一个参数，做了就是个假开关）。早先版本把「是否恒倒序」列为待答，已由 §4.7 关闭。
- **刷新 / 缓存 / 隐私**：进入本屏取一次；下拉刷新重取；无自动轮询、无 `>5min` 静默重取
  （TG-09 的缓存窗口只用于离线展示，不用来判定「要不要自动再拉一次」）。
  账目是**私有数据** ⇒ 缓存按 owner（principalId）分桶（D9），登出即随 generation 推进失效（D5/D8）；
  不写日志、不进通知（18）、不进截图脚本的常量表。本屏**全部为只读 GET**
  ⇒ 无幂等键（硬边界 5 不适用）、无写路径，符合硬边界 2「只读 GET 可直连」。
- **不得发明的字段/端点**：`cursor`、`nextCursor`、`total`、`offset`、`page`、`type` 的具体枚举值、
  `GET /api/me/credits/ledger/export`、`reason` 的中文本地化表（除契约 §4.6 已给的四条）、
  「按作品聚合消耗」端点 —— 无 ⇒ 不做、不渲染、不写文案。

## 8. 边界与文案

- **截断**：`reasonLabel` 1 行（AX 2 行）；其余为数字与短词，不截断。
- **极值**：100 条上限（列表恒 ≤100 行 ⇒ 无分帧渲染压力，无性能专项）；金额位数
  （四位数 `1280 co`）与「余额 %d」同位对齐靠 `type.mono`（TG-49 新档）；
  时间跨年 ⇒ 「YYYY年M月D日」（08 §8 口径的最后一档）。
- **零余额 / D12**：本屏**永不**出现「购买 / 充值 / 支付 / 价格 / 报价 / 升级 / 订阅管理 / 付款 /
  下单 / 优惠 / 限时 / ¥」任何字样；**不出现**「余额不足」（那是提交类屏的话术，本屏无提交）；
  余额位（`balanceAfter`）为 0 时正常显示「余额 0」，**不**用告警色、**不**加催促文案
  （11 §8 的关键落点：0 不是错误态）。
- **A15 术语**：只用 `co / 作品 / 任务` 词表；不出现「积分」「点数」「歌曲任务」等漂移词；
  「变动」是本屏新增的中性域词（描述 ledger 的每一行），不与 A15 词表冲突。
- **文案清单**（每串均过 `Scripts/d12-copy-check.sh` 禁词表；`重试` / `未同步` / `已显示全部` /
  `离线，展示上次内容` / `加载中…` / `--` 为 17 §10 与 11 的复用串）：
  `co 币明细` / `%d 条变动` / `其他变动` / `余额 %d` / `任务` /
  `这里只有最近 100 条变动` / `已显示全部` /
  `还没有变动记录` / `你的 co 变动会记在这里` / `做一首歌` / `明细没取到` / `重试` /
  `未同步` / `离线，展示上次内容` / `离线：明细需要联网` / `加载中…`
