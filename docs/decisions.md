| D21 | **登录的正确入口 = 两步，且两次响应的身份必须同源**（2026-09-24，用户点名「对照 web 代码确认正确的入口」后的实测结论）：① `POST /api/auth/login` 只**建立凭证**；权威身份与权益来自 `GET /api/auth/me`。iOS 原先把 `response.user` 写进会话状态 ⇒ 刚登录那一次缺 `covaId`/身份标记/权益，冷启动才补齐（两处口径不一致）。现 `signIn` = 建凭证 → `/me` → `state = .authenticated(me.user)`。② **`/me` 失败 ⇒ 登录未完成**：收回刚写入的凭证与 owner 态（`invalidateSession`），不留「状态说已登录、身份一无所知」的半态。③ **`me.user.id != login.user.id` ⇒ fail-closed**：两次响应不是同一个人时既不覆盖 principal（会把权益/缓存归属/上报 owner 记到别人身上）也不沿用 login 用户，抛 `CovaAPIError.decoding(field: "auth-me-user-id")` 并收回凭证。④ 顺带核实并采纳的 web 事实：refresh token **单次使用 + 旋转**（iOS 必须两条一起落盘，且**先 refresh 后 access**——见 D22③；原文写的是"每次成对落盘，已在刷新路径成立"，该主张于第 15 轮被 R15-5 否证：`SecureStore` 没有多键原子写，"成对"做不到，而当时的写序恰好把半态落在不可恢复的一侧）、`logout` 撤销**整个 session family**、服务端支持 Bearer（小程序同源用法，iOS 走 Bearer 合法）、另有 `POST /api/auth/device/code` + `/device/token` 的**设备授权流**（为非浏览器客户端设计，v1.0 不引入：邮箱口令登录已可用，引入会扩大凭证面）。⑤ **NEEDS-1 撤销**（登记为后端缺口是误判，见 `docs/NEEDS.md` #1 的关闭说明）| 用户给出测试账号并要求对照 web；对照结果是"客户端入口用错"而非"后端缺字段"。留着错误入口会让登录后的整条链路（私有音频 D7 / 上报 / 会员权益）在验收时表现出"权限看不见"的假象 | ⚙️ 协调者专业裁决（2026-09-24），待第 15 轮隔离复审与用户看效果确认 |
| D22 | **会话提交的判据、失败登录的两种收尾，与旋转凭证的写序**（第 21 批，R15-1/4/5 的专业裁决）：① `signIn` 写 `state` 之前**只**同步复核 `sessionEpoch`——本 actor 内每一条"用户可感知的会话变化"（显式登出 / 选游客 / 凭证吊销 / 任一提交）都在同步上下文里推进它，所以同步读它就是终态判定。**刻意不把 `generation` 并进取提交判据**：`restoreSession` 会推进 generation 却不推进 epoch（被动的冷启动恢复不算用户动作），拿它当判据会让一次迟到的冷启动恢复把用户**主动**点的登录判废 —— 方向正好相反。这条取舍由 `testGenerationAdvanceWithoutEpochStillCommitsTheExplicitLogin` 反向钉住。② 登录没完成时分两种收尾：**会话仍归本次登录** → `invalidateSession`（状态转 `signedOut` + 生命周期清理）；**已被别的会话变化接管** → 只做定点回滚（删自己的凭证 + owner 指针仍指向自己时才清），绝不改全局状态，否则就把赢家（往往是用户最后那一下真实操作）的会话抹掉。定点回滚删凭证前 best-effort 打一次 `/api/auth/logout`：本地删 token ≠ 服务端会话结束。③ 两条凭证的落盘次序固定为 **先 refresh 后 access**（登录与刷新路径同一口径）：`SecureStore` 没有多键原子写，半态不可避免，那就只能落在**可恢复**的一侧 —— 反过来写留下「新 access + 已被服务端消费掉的旧 refresh」⇒ 刷新永久坏；现在留下的是「旧 access + 新 refresh」⇒ 旧 access 过期后还能续上。④ 回滚/失效的清理失败**必须冒到调用方**（`invalidateSession` 改为返回 `SessionCleanupFailure?`，`concludeFailedSignIn` 在清理失败时改抛它而非登录错误）：状态已经转 `signedOut` 而库里还有活凭证时，用户看到的必须是"清理没做完"，`try?` 吞掉等于自我安慰 | 第 15 轮两个零网络确定性探针给出确定性后果（显式登出被在途登录推翻、并发登录两账号导致状态与 owner 指针分家 ⇒ 此后每个请求都不带 Authorization）；③④ 是评审实测的等价变异与写序风险。都不改后端、不改契约 | ⚙️ 协调者专业裁决（2026-09-24，第 21 批），待第 16 轮隔离复审 |
