**4 个包是否必须同时落地？结论：必须。**
- 依据 D3（🔒 锁定四层）与 PLAN G3（四层即四项交付物）；分层的全部价值来自"边界被强制"，
  若本次只落 `CovaCore`，G3 再引入其余三层时 App/Feature 侧代码极可能已越界，代价是返工。
- 现在落地成本极低（4 个 `Package.swift` + 4 个占位类型）。
- 备选"单包多 target"能表达同样方向，但任务书要求逐包 `Package.swift`，且独立包对
  "白名单为空"的零外部依赖边界更清晰 → 不采用。

**惯性冗余（本次不做）**：UI 测试 / 快照测试（G1/G2 未过无 UI 可测，硬边界 8）；

## 4. 冲突处理（含实测结论）

1. **`.gitignore` 的 `Packages/` vs 本地源码包入库** → 已改为只忽略 `.swiftpm/`、`.build/`、
   `Packages/**/.build/`、`Package.resolved`。属本仓内配置冲突，**非后端缺口**，不写 NEEDS。
2. **官方品牌资产 `CovaAssets.xcassets` 缺根 `Contents.json`** → 实测 actool 正常接受，
   产出 `Assets.car` 与 AppIcon PNG，**无需修改官方资产**（"只引用不得修改"得以保持）✔
3. **Xcode 不强制本地包的分层边界（真实缺陷，已闭环）**：实测在 `CovaCore` 里写
   `import CovaUI`（未声明依赖）时，`xcodebuild ... build` 仍 **BUILD SUCCEEDED**；
   而 `swift build --package-path Packages/CovaCore` 正确报 `no such module 'CovaUI'`。
   → 结论：Xcode 集成本地包时会放宽模块可见性，**不能只靠编译器**。已在 `check.sh` 增加
   3/5 静态边界门禁（校验各包 `Package.swift` 声明 + 源码 `import` 两侧），并做了两次负向
   验证（声明违规 / import 违规均被拦截并非零退出）。
4. **`CFBundleShortVersionString` 作为自定义 build setting 是否被 Info.plist 展开** → 实测生效
   （产物 plist `0.1.0`），无需退回 `MARKETING_VERSION`。
5. **Bash 3.2 变量名后紧跟中文全角字符会被并入变量名**（`$SIM_NAME）` → `unbound variable`）
   → `check.sh` 统一改用 `${VAR}` 花括号写法。踩坑记录。
6. **G0 闸门 D1/D12 仍为 ⏳ 未批准** → 不阻塞本次（D1 部署目标由任务硬约束给定；D12 只约束
   UI 购买入口，本任务无 UI）；**上报协调者**：PLAN G0 勾选前需用户裁决 D1/D12。
7. **D13 显示名未定** → 占位 `CFBundleDisplayName = Cova`，待设计阶段定稿；非后端缺口，不写 NEEDS。
8. **未新增 `docs/NEEDS.md` 条目**：本任务零网络请求，无接口/字段/契约接触面。

## 3. M3 的关键发现：Xcode 不为本地 SwiftPM 包产出 xccov 覆盖率

要求原文为「解析 xcresult / xccov」。经 **6 组实验**确认该路径在本工具链下**不可达**，故换了测量路径：

1. 应用工程 test + `gatherCoverageData` → xccov 报告只有 `Cova.app` / `CovaTests.xctest`，**无包源码**。
2. 检查 `CovaCore.o`：**无** `__llvm_covmap`/`__llvm_prf_*` 段（测试目标对象有）→ 包目标根本没被插桩。
3. 临时给 `CovaCore` 加真实函数后重测：xccov 仍**不含** CovaCore（排除「无可执行行」解释）。
4. 命令行 `CLANG_ENABLE_CODE_COVERAGE=YES` 覆盖：对象**有**了 5 个覆盖率段，但机器码内**无** `CovaEnvironment.swift`
   的 covmap 字符串、`xccov --archive --file-list` 也**没有**该文件 → 覆盖率映射在链接/收集阶段被丢弃。
5. 再叠加 `DEAD_CODE_STRIPPING=NO` / `OTHER_LDFLAGS=-fprofile-instr-generate`：仍为 `CovaCore 0.00% (0/0)`。
6. 包作用域 `xcodebuild -scheme CovaCore -destination 'iOS Simulator' -enableCodeCoverage YES`：同样 0/0。

结论：`xccov` 无法测量本地包；**SwiftPM 自身插桩有效**（实验证实），故门禁改为
`swift test --package-path Packages/CovaCore --enable-code-coverage` + `xcrun llvm-cov export --format=lcov`，
按 `Packages/CovaCore/Sources/` 过滤后算行覆盖率并断言 ≥80%。被测源码与 iOS 运行完全同一份；
`CovaCore` 因此声明 `.macOS(.v14)`（仅为宿主侧测量；iOS 仍是产品目标平台）。

**这是对评审 M3 要求字面（xccov）的偏离，属工具链限制而非绕过**，请协调者裁决是否登记 `decisions.md`。
若坚持 xccov 路径，需先解决 Xcode 不为本地包插桩的问题（换 Xcode 版本或改包集成方式）。

## 二、根因（逐条）

1. **命名假设（C1）** — 第一轮用 `find -name 'CovaCorePackageTests'` 发现测试二进制。该名字是
   **Xcode 26.6 / 旧 SwiftPM 布局**（`.build/debug/<Pkg>PackageTests.xctest`）的产物；Xcode 27 的 SwiftPM
   改为 `.build/out/Products/Debug/<Target>Tests.xctest`（目录布局与名字都变了）。
   错误本质：把「当时实测到的具体文件路径」当成稳定契约，而**不用工具自己提供的稳定锚点**
   （`swift test --show-codecov-path` / `swift build --show-bin-path`）。属**取证绑定工具链版本、锚点选错**。
2. **阈值可覆盖（M3-a）** — `CORE_COVERAGE_MIN="${COVA_CORE_COVERAGE_MIN:-80}"` 允许把阈值降到 0。
   错误本质：把「本地调试方便」凌驾于 fail-closed 之上；阈值型门禁必须**只能抬高、不能降低**。
3. **口径错配（M3-b）** — 覆盖率测量跑在 **macOS 主机产物**上，而产品是 iOS。`#if os(iOS)` 的代码在
   macOS 编译中根本不存在，测量面 ⊊ iOS 编译面。实测注入 iOS-only 函数后仍 100%。
   错误本质：为绕开「Xcode 不插桩本地包」而选了宿主测量路径，却没有同时**强制被测量代码平台中立**。

## 三、为什么现有门禁无法自证（为何第一轮全部逃过）

第一轮的自证方法是「往**被检查的代码**注入缺陷 → 看退出码」。而这批缺陷攻击的是**门禁自身**：

- C1 只在**工具链版本变化**时暴露。第一轮自证与实现发生在同一台机器、同一 Xcode 26.6 上，
  等于**用同一把尺子量自己**；而 `check.sh` 从未在「干净克隆 + 当前工具链」下跑过
  （第一轮的克隆验证也发生在 26.6 时期）——恰恰违反 G0 终态「任一环境一条命令可复现」的初衷。
- M3-a/M3-b 的注入对象是**门禁参数**（环境变量）与**测量口径**（宿主 vs 产品平台），不是被测源码，
  第一轮的矩阵里根本没有这两类用例。
- m3/m4/m5 同理：它们不改变被测代码语义，只改变门禁的**判定输入**（日志文本、target 书写顺序、
  覆盖率报告里的 0/0 行），因此「注入源码缺陷」的玩法永远碰不到。

→ 自证矩阵必须补三类用例：**工具链形态无关性**（产物名/布局变化）、**门禁参数不可放宽**、
**测量口径与产品平台一致**。这也是本轮验证策略的主轴。

## 四、对上一节「修复策略」的更正（不隐瞒）

上一节原计划用 SwiftPM `--xunit-output` 作为覆盖率运行的可信计数源。实测（Swift 6.4）该开关**只写 Swift Testing 结果**
（`<path>-swift-testing.xml`，本仓 XCTest 用例记 0），因此改用**结构化覆盖率数据**证明测试确实执行
（测试源码命中行数 > 0，`:323-338`）。两个 xcodebuild 运行的计数仍走 xcresult（`executed=2`/`executed=4`），
全门禁已无任何「以日志文本计数」的判定。

## 五、遗留 / 存疑（不隐瞒）

- C1 的「布局变化免疫」以本轮 Xcode 27 实测 + 旧布局（Xcode 26.6）已不存在为前提；发现逻辑含两级 fallback，
