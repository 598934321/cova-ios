**4 个包是否必须同时落地？结论：必须。**

- 现在落地成本极低（4 个 `Package.swift` + 4 个占位类型）。
- 备选"单包多 target"能表达同样方向，但任务书要求逐包 `Package.swift`，且独立包对
  "白名单为空"的零外部依赖边界更清晰 → 不采用。

**惯性冗余（本次不做）**：UI 测试 / 快照测试（G1/G2 未过无 UI 可测，硬边界 8）；

## 4. 冲突处理（含实测结论）

1. **`.gitignore` 的 `Packages/` vs 本地源码包入库** → 已改为只忽略 `.swiftpm/`、`.build/`、
   `Packages/**/.build/`、`Package.resolved`。属本仓内配置冲突，**非后端缺口**，不写 NEEDS。
2. **官方品牌资产 `CovaAssets.xcassets` 缺根 `Contents.json`** → 实测 actool 正常接受，
   产出 `Assets.car` 与 AppIcon PNG，**无需修改官方资产**（"只引用不得修改"得以保持）✔
3. **Xcode 不强制本地包的分层边界（真实缺陷，已闭环）**：实测在 `CovaCore` 里写
   `import CovaUI`（未声明依赖）时，`xcodebuild ... build` 仍 **BUILD SUCCEEDED**；
   而 `swift build --package-path Packages/CovaCore` 正确报 `no such module 'CovaUI'`。
   → 结论：Xcode 集成本地包时会放宽模块可见性，**不能只靠编译器**。已在 `check.sh` 增加
   3/5 静态边界门禁（校验各包 `Package.swift` 声明 + 源码 `import` 两侧），并做了两次负向
   验证（声明违规 / import 违规均被拦截并非零退出）。
4. **`CFBundleShortVersionString` 作为自定义 build setting 是否被 Info.plist 展开** → 实测生效
   （产物 plist `0.1.0`），无需退回 `MARKETING_VERSION`。
5. **Bash 3.2 变量名后紧跟中文全角字符会被并入变量名**（`$SIM_NAME）` → `unbound variable`）
   → `check.sh` 统一改用 `${VAR}` 花括号写法。踩坑记录。
6. **G0 闸门 D1/D12 仍为 ⏳ 未批准** → 不阻塞本次（D1 部署目标由任务硬约束给定；D12 只约束
   UI 购买入口，本任务无 UI）；**上报协调者**：PLAN G0 勾选前需用户裁决 D1/D12。
7. **D13 显示名未定** → 占位 `CFBundleDisplayName = Cova`，待设计阶段定稿；非后端缺口，不写 NEEDS。
8. **未新增 `docs/NEEDS.md` 条目**：本任务零网络请求，无接口/字段/契约接触面。

## 3. M3 的关键发现：Xcode 不为本地 SwiftPM 包产出 xccov 覆盖率

要求原文为「解析 xcresult / xccov」。经 **6 组实验**确认该路径在本工具链下**不可达**，故换了测量路径：

1. 应用工程 test + `gatherCoverageData` → xccov 报告只有 `Cova.app` / `CovaTests.xctest`，**无包源码**。
2. 检查 `CovaCore.o`：**无** `__llvm_covmap`/`__llvm_prf_*` 段（测试目标对象有）→ 包目标根本没被插桩。
3. 临时给 `CovaCore` 加真实函数后重测：xccov 仍**不含** CovaCore（排除「无可执行行」解释）。
4. 命令行 `CLANG_ENABLE_CODE_COVERAGE=YES` 覆盖：对象**有**了 5 个覆盖率段，但机器码内**无** `CovaEnvironment.swift`
   的 covmap 字符串、`xccov --archive --file-list` 也**没有**该文件 → 覆盖率映射在链接/收集阶段被丢弃。
5. 再叠加 `DEAD_CODE_STRIPPING=NO` / `OTHER_LDFLAGS=-fprofile-instr-generate`：仍为 `CovaCore 0.00% (0/0)`。
6. 包作用域 `xcodebuild -scheme CovaCore -destination 'iOS Simulator' -enableCodeCoverage YES`：同样 0/0。

结论：`xccov` 无法测量本地包；**SwiftPM 自身插桩有效**（实验证实），故门禁改为
`swift test --package-path Packages/CovaCore --enable-code-coverage` + `xcrun llvm-cov export --format=lcov`，
按 `Packages/CovaCore/Sources/` 过滤后算行覆盖率并断言 ≥80%。被测源码与 iOS 运行完全同一份；
`CovaCore` 因此声明 `.macOS(.v14)`（仅为宿主侧测量；iOS 仍是产品目标平台）。

**这是对评审 M3 要求字面（xccov）的偏离，属工具链限制而非绕过**，请协调者裁决是否登记 `decisions.md`。
若坚持 xccov 路径，需先解决 Xcode 不为本地包插桩的问题（换 Xcode 版本或改包集成方式）。

## 二、根因（逐条）

1. **命名假设（C1）** — 第一轮用 `find -name 'CovaCorePackageTests'` 发现测试二进制。该名字是
   **Xcode 26.6 / 旧 SwiftPM 布局**（`.build/debug/<Pkg>PackageTests.xctest`）的产物；Xcode 27 的 SwiftPM
   改为 `.build/out/Products/Debug/<Target>Tests.xctest`（目录布局与名字都变了）。
   错误本质：把「当时实测到的具体文件路径」当成稳定契约，而**不用工具自己提供的稳定锚点**
   （`swift test --show-codecov-path` / `swift build --show-bin-path`）。属**取证绑定工具链版本、锚点选错**。
2. **阈值可覆盖（M3-a）** — `CORE_COVERAGE_MIN="${COVA_CORE_COVERAGE_MIN:-80}"` 允许把阈值降到 0。
   错误本质：把「本地调试方便」凌驾于 fail-closed 之上；阈值型门禁必须**只能抬高、不能降低**。
3. **口径错配（M3-b）** — 覆盖率测量跑在 **macOS 主机产物**上，而产品是 iOS。`#if os(iOS)` 的代码在
   macOS 编译中根本不存在，测量面 ⊊ iOS 编译面。实测注入 iOS-only 函数后仍 100%。
   错误本质：为绕开「Xcode 不插桩本地包」而选了宿主测量路径，却没有同时**强制被测量代码平台中立**。

## 三、为什么现有门禁无法自证（为何第一轮全部逃过）

第一轮的自证方法是「往**被检查的代码**注入缺陷 → 看退出码」。而这批缺陷攻击的是**门禁自身**：

- C1 只在**工具链版本变化**时暴露。第一轮自证与实现发生在同一台机器、同一 Xcode 26.6 上，
  等于**用同一把尺子量自己**；而 `check.sh` 从未在「干净克隆 + 当前工具链」下跑过
  （第一轮的克隆验证也发生在 26.6 时期）——恰恰违反 G0 终态「任一环境一条命令可复现」的初衷。
- M3-a/M3-b 的注入对象是**门禁参数**（环境变量）与**测量口径**（宿主 vs 产品平台），不是被测源码，
  第一轮的矩阵里根本没有这两类用例。
- m3/m4/m5 同理：它们不改变被测代码语义，只改变门禁的**判定输入**（日志文本、target 书写顺序、
  覆盖率报告里的 0/0 行），因此「注入源码缺陷」的玩法永远碰不到。

→ 自证矩阵必须补三类用例：**工具链形态无关性**（产物名/布局变化）、**门禁参数不可放宽**、
**测量口径与产品平台一致**。这也是本轮验证策略的主轴。

## 二、为什么「枚举 iOS-only 模式」必然不完备

条件编译是一个**开放的表达式空间**，而枚举是黑名单：只要存在一个语义等价但字面不同的写法，就漏检。

| 类别 | 反例（都是 iOS-only 语义，但字符串形态各异） |
|---|---|
| 否定式 | `#if !os(macOS)`（本轮实测绕过）、`#if !canImport(Darwin)`、`#if !targetEnvironment(macCatalyst)` |
| 分支链 | `#if os(macOS) … #elseif os(iOS) … #else`；iOS-only 代码写在 `#else` 分支里，条件里没有 `os(iOS)` |
| 平台声明式 | `Package.swift` 的 `swiftSettings: [.define("IOS_BUILD", .when(platforms: [.iOS]))]` → 源码里只有 `#if IOS_BUILD`，**完全不出现平台名**（评审第二向量） |
| 组合式 | `#if canImport(UIKit) && os(iOS)`、`#if os(iOS) \|\| os(tvOS)` |
| 嵌套/自定义 | 嵌套 `#if`、`#if DEBUG` 配合 `.define`、`#if compiler(>=6.0)`、`#if hasFeature(…)` |
| 导入侧 | `@_exported import UIKit`（跨模块再导出）、`#if canImport(UIKit) import UIKit #endif` |
| 其它平台名 | `os(visionOS)`、`os(tvOS)`、`targetEnvironment(macCatalyst)` |

后果的特殊性：**漏检是静默的** —— 覆盖率仍报 100%、门禁给虚假信心，比编译报错危险得多。
且维护成本随 Swift 演进而线性增长（每出现一个新平台/新特性条件就要补一条正则），第二轮的
16 项模块白名单 + 一条正则正是这种「追着表达空间跑」的典型失败形态。

## 三、结论：门禁必须改为不变量式（禁止整个类别）

依据：D3 定义 `CovaCore` 为**纯逻辑层**（模型/API/认证/SSE/幂等/持久化）；D9 持久化 = Codable + 沙盒文件；
PLAN G3 要求「纯逻辑全 XCTest」。**纯逻辑层不需要任何平台条件编译**。因此门禁不变量为：

1. `CovaCore/Sources/` 与 `CovaCore/Tests/` 中**不得出现任何条件编译指令**
   （`#if` / `#elseif` / `#else` / `#endif`，剥注释与字符串后判定）—— 约束的是**类别**，不是形态清单。
2. `CovaCore/Package.swift` 不得含平台条件构建设置（`.when(platforms:`、`.define(`、`.unsafeFlags(`）；
   平台声明必须恰为 `.iOS(.v26), .macOS(.v14)`，且 `.macOS` 的唯一用途（宿主侧覆盖率测量）
   由门禁文案与源码注释共同说明。
3. 既有 iOS-only 模块 import 禁令保留，作为第二道防线。
4. 若 G3 真实需求与不变量冲突 → **不得静默放宽**，登记 `docs/NEEDS.md` / `decisions.md` 交协调者裁决
   （本仓现有唯一相关技术债见文末「技术债清单」的 CovaPlayer 条目）。

与枚举的本质区别：不变量是**类别禁用**（白名单式的结构性约束），不追赶表达空间；任何新写法
在**静态阶段（7/8）**即非零退出，而不是等覆盖率悄悄失真之后。

## 二、为什么手写状态机必然有洞

逐字符状态机要正确，必须枚举**所有**会改变「引号/注释状态」的字面量形态；而 Swift 的形态空间是
开放且可互相嵌套的：

| 形态 | 为什么状态机失步 |
|---|---|
| 单行 raw string `#"…"#`（`#` 可任意个：`##"…"##`） | 状态机不知道 `#` 前缀存在；内容里的引号被当成字符串边界，引号奇偶错位 → 失步（**本轮 F1**） |
| 多行 raw string `#"""…"""#` | 同上，且跨行 |
| 字符串插值 `"\(expr)"` / `#"\(expr)"#` | 插值内部可再含字符串、注释，状态需递归 |
| 转义 `\"` / `\\` / `\u{…}` | 反斜杠规则与 raw string 中「反斜杠不转义」的规则相反 |
| 多行字符串 `"""…"""` 内含引号 | 需要三引号成对判定 |
| CRLF、不可见 Unicode、极长行 | 行尾/缓冲处理遗漏即失步 |

**致命点**：一旦 `in_str`/`in_block` 在某处翻转错位，**该文件其余内容全部被当作文本剥掉**
（或反之），于是 `#if` / `import` / `func test*` 一起隐形。根本缺陷不是「少枚举了一种形态」，
而是**把安全不变量建立在一个未被证明正确的自定义词法之上** —— 门禁正确性依赖全称命题
「我的状态机覆盖了所有 Swift 字面量形态」，这无法用测试穷尽（每加一种形态就多一个反例空间）。

## 三、结论：自定义词法不得作为安全不变量 → 改用不可失步的判定

1. **删除** `Scripts/swift-scan.awk` 及其全部调用；**不再引入任何逐字符状态机/词法**。
2. **条件编译不变量**：CovaCore 的 `Sources/` 与 `Tests/` 中，只要文件含字面量 `#if` 即失败
   （固定字符串递归匹配）。理由：Swift 的条件编译指令必然是字面 `#if`，无法被字符串/注释/编码伪装；
   且不存在没有 `#if` 的 `#elseif/#else/#endif`。注释里出现 `#if` 也判失败 —— **故意的 fail-closed**，
   已写入脚本注释。
3. **iOS-only 框架禁令与分层依赖方向**：不做词法剥离，直接正则匹配，**接受注释误报**并 fail-closed
   （误报处理方式写入脚本注释）。
4. **测试数量下限**：删除全部 `declared` 源码统计逻辑，改为**只用 xcresult 的 executed 计数**与
   入库基线 `Scripts/test-count-baseline.env` 比较（保留 `>= 1`）；覆盖率运行另以「测试源码命中行数 > 0」
   这一结构化数据佐证测试确实执行。
5. **有效构建设置**：Debug 与 Release 两个 configuration 都断言（发布归档走 Release）。

**不可失步的理由**：固定字符串/正则匹配没有跨行状态，任何字符序列都不会让它「翻转后失效」；
误报方向永远是「失败」而不是「放行」。

# 根因分析（第五轮复审红线：文本正则不可收敛）

> 上轮「字面 #if 固定匹配」已被验证不可失步（8 种形态全命中），但本轮又冒出 4 个新变体。
> 方法论问题：**门禁在用正则对抗一门开放语法的文本**，这是无限追逐。

## 一、为什么「正则匹配源码/配置文本」必然发散

同一个语义有无穷多合法写法；每修一个变体，只是新增一个待发现的变体：

| 事实 | 本轮的绕过写法 | 为什么正则追不上 |
|---|---|---|
| 「CovaCore 不含 iOS-only 代码」 | target 加 `sources: ["Sources/CovaCore", "Extra"]`，`Extra/PlatformEvil.swift` 里放 `#if os(iOS)+import RealityKit` | 扫描范围是**路径白名单**（只扫 Sources/Tests），语法的自由度在「文件位置」上 |
| 「实际用 Swift 6 构建」 | `SWIFT_VERSION[sdk=iphonesimulator*]: "5.0"`、`OTHER_SWIFT_FLAGS: "-swift-version 5"` | 构建设置是**条件求值**的（sdk/config/arch 维度），读单一取值永远漏 |
| 「包语言模式 = v6」 | 包级 `swiftLanguageModes: [.v6]` 保留，target 加 `swiftSettings: [.swiftLanguageMode(.v5)]` | 同一事实有**多层声明**（package / target / 编译参数），清单式枚举漏层 |
| 「依赖方向合法」 | `.package(path : "../CovaPlayer")`（冒号前空白）+ `import/* 注释 */CovaPlayer` | 合法语法允许**任意空白与注释穿插**，正则要么过严（误报）要么过松（漏检） |
| 「零第三方依赖」 | project.yml `packages: EvilPkg: { path: /tmp/evilpkg }`（仓外本地包） | 正则匹配的是「已知形态字面」，新形态（本地外部包）不在枚举内 |

**根本矛盾**：文本正则在近似「词法层」的判定上不可靠（第四轮已证），在「语义/条件求值层」的判定上
更是不可靠（本轮 4 例）。继续补正则是把维护成本线性外推给未来每一轮评审。

## 二、结论：能用机器可读产物表达的事实，一律不得用文本正则判定

| 事实类别 | 权威机器可读产物（本轮改用） | 文本判定是否保留 |
|---|---|---|
| 依赖方向 / 依赖类型 / 平台声明 | `swift package dump-package`（JSON；本机 `plutil` 可解析，无需第三方） | **否**（删除正则） |
| 实际编译语言版本 | **实际构建日志**：Xcode `*.xcactivitylog`（gunzip + strings）与 SwiftPM `swift test -v` 的 `-swift-version N` | 只判「取值集合 = {6}」 |
| 实际被编译的文件集合 | SwiftPM `.SwiftFileList` 产物 | 与扫描集合做一致性断言 |
| 有效构建设置（含 sdk/config 条件） | `xcodebuild -showBuildSettings`（与实际构建**同一 sdk/destination**，且两配置都查） | 只判「字面令牌不得出现」（如 `-swift-version`） |

# 根因分析（第六轮复审红线：扫描域应为编译文件集合）

> 「平台中立性扫描范围」已存活 4 轮。根因：门禁扫的是**目录**，而权威事实是**实际被编译的文件集合**。

## 一、复现（修复前实测，Xcode 27.0 / Swift 6.4）

**W1（仓内相对符号链接）**

```bash
mkdir -p Packages/evilcore
printf '#if os(iOS)\nimport UIKit\n\npublic enum PlatformBridge {\n    public static func hidden(_ x: Int) -> Int { x * 7 }\n}\n#endif\n' > Packages/evilcore/PlatformBridge.swift
ln -s ../../../evilcore Packages/CovaCore/Sources/CovaCore/LinkedExternal   # 指向 Packages/evilcore（包外）
./Scripts/check.sh
```

| 观察点 | 实测 |
|---|---|
| `grep -rn '#if' Packages/CovaCore --exclude-dir=.build` | **0 命中**（BSD `grep -r` 不跟随符号链接） |
| `grep -rnw UIKit Packages/CovaCore …` | **0 命中** |
| `swift build -v` | `PlatformBridge.swift` **被编译**（SwiftPM 跟随符号链接） |
| `.SwiftFileList` 记录 | **词法路径** `…/Packages/CovaCore/Sources/CovaCore/LinkedExternal/PlatformBridge.swift` → 前缀断言恒真（打印「编译集合一致」） |
| 端到端 | **PRE_FIX_W1_GATE_EXIT=0**，`CovaCore 行覆盖率：7/7 = 100.00%` |

**Minor-1（`exclude:` 收缩覆盖率分母）**：`exclude: ["HardToTest.swift"]` → 该文件从 lcov 消失、目录扫描仍能看到它（无 `#if`/iOS-only 令牌故不触发）→ 覆盖率报 100%，**EXIT=0**。

**Minor-2（其它 Swift 编译开关降级严格并发）**：`OTHER_SWIFT_FLAGS: "-strict-concurrency=minimal"` → 门禁读到的有效设置是
`SWIFT_STRICT_CONCURRENCY=complete`；实际 swiftc 调用是 `-strict-concurrency\=minimal`（xcactivitylog 实证，日志里 `=` 被转义）
→ 门禁无感，**EXIT=0**。

## 二、为什么「扫目录」≠「实际编译集合」

| 机制 | 扫目录（`grep -r` / `find`） | 编译（SwiftPM / Xcode） |
|---|---|---|
| 目录符号链接 | **不跟随**（漏检） | 跟随并编译 |
| 链接指向包外目录 | 目录树里根本看不到 | 文件被编译进目标 |
| `exclude:` / `sources:` 收缩 | 文件仍在目录里（可能被扫到但**不在分母**） | 不编译 → 覆盖率分母消失 |
| `.SwiftFileList` 记录形态 | — | **词法路径**（不解析符号链接）→ 前缀断言恒真 |

结论：目录与编译集合是**两个不同的集合**，且可被符号链接/排除项/包外路径任意拉开差距。
权威事实只有 `.SwiftFileList`（实际被编译的文件清单）；扫描域必须是它，且必须 **`realpath` 解析符号链接后**再做前缀与集合断言。

## 三、结论（本轮不变量）

1. **平台中立性（字面 `#if` + iOS-only 令牌）判定改为逐个扫描 `.SwiftFileList` 中的实际编译文件**（`realpath` 后读取内容），不再以目录为准。
2. **双向集合校验**：`realpath(编译集合)` == `realpath(CovaCore 源目录下 .swift 全集，排除 Tests/.build)`；
   任何符号链接、`exclude:` 收缩、包外源文件 → 非零退出。
3. **覆盖率分母校验**：源目录 .swift 真实路径全集 ⊆ lcov 的 `SF:` 条目集合（Minor-1）。
4. **严格并发**：实际编译日志（xcactivitylog / SwiftPM `-v`）中任何 `-strict-concurrency` 令牌的值必须为 `complete`；
   并在有效构建设置层禁用 `OTHER_SWIFT_FLAGS` 里的 `-strict-concurrency` 令牌（快速兜底）。
5. 目录级扫描保留为 **3/8 的早期兜底**（快速失败、信息友好），但**不再是唯一防线**。

# 根因分析（第七轮复审：门禁误红与空谓词）

> 本轮 Major 是**上一轮修复引入的误红**。误红与漏检同等严重：维护者会被迫反向放宽门禁，等同削弱防线。

## 一、复现（修复前实测，Xcode 27.0 / Swift 6.4）

| 用例 | 注入 | 实测 |
|---|---|---|
| **Major-1** 纯声明文件误红 | `PureDecls.swift`（protocol + 空 enum + 仅 case 枚举）、`ErrorOnly.swift`（仅 case 的错误枚举）、`EmptyFile.swift`（0 字节）、`CommentOnly.swift`（仅注释） | 双向集合校验**通过**（`编译集合与源集合双向一致：5 个文件`），但 lcov 无 `SF:` → **EXIT=1**，文案误导为「可能被 exclude:/sources: 收缩」 |
| **Minor-2a** 点号目录误红 | `Packages/CovaCore/.cache/HiddenCache.swift`（SwiftPM 忽略点号目录） | `SOURCES` 含它、`COMPILED` 不含 → **EXIT=1**（双向集合误报） |
| **Minor-2b** `.build` 为符号链接误红 | `ln -s /tmp/shared-build Packages/CovaCore/.build`（共享 build cache 布局） | `find -type l -not -path '*/.build/*'` 把 `.build` **自身**判为违规链接（该 pattern 不匹配目录本身）→ **EXIT=1** |
| **Minor-1** 空谓词 | 干净构建日志统计 `-strict-concurrency` 次数 | `build.log: 0`、`test-core-coverage.log: 0` → 断言恒真，但文案宣称「实际编译日志取值必须是 complete」 |

## 二、根因（逐条）

1. **「源文件必须出现在 lcov SF 中」是不可满足的全称断言**：llvm-cov 只为**含可执行区域**的文件产出 `SF:`
   （protocol / 空枚举 / 仅 case 枚举 / 仅错误枚举 / 0 字节 / 仅注释 → 无 `SF:`）。
   「被编译」是**编译事实**，「进入覆盖率分母」是**插桩事实**，二者不是同一集合。
2. **该断言还是冗余的**：`exclude:` / `sources:` 收缩必然先破坏「编译集合 == 源集合」双向校验
   （上一轮 W1c/W1d 实测均在此被拦）；SF 断言的净效果只是在**合法文件**上制造误红。
3. **「实际编译 strict-concurrency 令牌」是空谓词**：Swift 6 语言模式已隐含 complete，Xcode **不主动输出**
   该 flag（只有显式注入 `OTHER_SWIFT_FLAGS` 时才出现——上一轮 m2a 的日志里确实出现过 `-strict-concurrency\=minimal`）。
   「缺数据即通过 + 宣称已校验」是不诚实的表述。
4. **枚举规则未与 SwiftPM 对齐**：SwiftPM 忽略点号目录/文件；门禁 `find` 会进入点号目录；
   `-not -path '*/.build/*'` 不匹配 `.build` 自身（目录条目无尾斜杠）。
5. **总根因（方法论）**：门禁对「工具链语义」的假设（哪些文件进分母、哪个 flag 会出现、哪些路径被忽略）
   以「我期望的行为」为准，而非工具的真实行为。**误红与漏检同源**，都必须以实测为准收敛。

## 三、结论与修复策略

1. **删除** SF 完备性断言（`:491-501` 及其 `LCOV_SF`）；`exclude:`/`sources:` 收缩继续由
   「编译集合 == 源目录 .swift 全集」双向校验拦截（**保留**该断言，已在 W1c/W1d 验证有效）。
2. **文案据实**（Minor-1 方案 a）：`-strict-concurrency` 检查改为
   「**若**出现该令牌则必须为 complete（Swift 6 模式下 Xcode 通常不输出，此时不构成实际校验）」；
   保留该检查（能拦下显式注入，成本为零），但不再宣称「已实际校验」。
3. **枚举规则与 SwiftPM 对齐**（Minor-2）：符号链接禁令与源集合枚举统一排除「点号路径分量」
   （`-not -path '*/.*'`）→ 同时排除 `.build` 自身与其内部、以及 SwiftPM 忽略的点号目录/文件。
   **不重新打开 W1**：SwiftPM 不编译点号目录，故编译集合不会出现点号路径；若有人把点号路径显式列入
   `sources:`，则「编译集合 == 源集合」仍不成立 → fail-closed 不变。
4. **自证必须含「合法工程不得误红」对照**（本轮起固定纳入矩阵）。
