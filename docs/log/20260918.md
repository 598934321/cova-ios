## 一、终态（用户可感知的结果）

`./Scripts/check.sh` 与「协调器套件高倍重复」两条口径下都**确定性全绿**，且测试仍然有杀伤力：
- 协调器套件的任何一次执行结果与调度顺序无关（同一代码同一虚拟时间序列 → 同一结论）；
- 破坏生产守卫（SSE/轮询取消守卫、降级 phase 守卫）必须让对应用例变红（变异自证）；
- 测试数量与基线不下调（`CORE_MIN` ≥ 372，净测试数不减少）。

## 二、最小机制

1. **把「等待」从轮询式改为信号式**：所有「任务已开始 / 已完成 / 已退出 / 第 n 个周期已到」都改成
   被测代码注入点或回调产生的事件（actor 内 `withCheckedContinuation` 挂起 → 事件到达才唤醒）。
2. **把「推进时间」从步进改为跳转**：先等目标定时器**注册**（`sleep` 注册事件），再跳到它的截止时刻；
   不做 1s 步进猜测，因而没有「注册空窗」与「推进过冲」。
3. **断言只针对必然成立量**：必然量来自状态机纯逻辑（phase/degradedBy/周期计数/去重签名）与
   「信号已到达」这一事实，而不是「让出 N 次调度之后大概就到了」。
4. **必须验证「没有发生某事」时，先建立确定性处理边界**：
   - 任务体退出边界 → 结束注入点（TD-34 扩展 `setAfterSSETaskEnd` / `setAfterPollTaskEnd`）；
   - 状态机写入边界 → 轮询周期信号（`performPoll` 同步自增周期计数后才创建任务）；
   - 定时器边界 → `advanceToNextDeadline` 放行计数 + 后续信号。
5. 冗余的惯性写法（`for _ in 0..<300 { await Task.yield() }`、`advanceUntil` 1s 步进、
   `assertEventually` 有界让步断言）全部移除（`advanceUntil`/`assertEventually` 删除；
   `waitUntil` 仅保留给「OS 线程事件」的尽力观测，明确禁止作断言依据）。

## 三、假设清单（逐条对证）

| # | 假设 | 对证 |
|---|---|---|
| A1 | 「`Task.yield()` N 次后目标任务必然推进到某点」 | **假**。让步只让出执行权，不保证任何特定任务被调度到；高负载下 N 次让步可全部落空。原 6 个 flake 用例的主要失败机制。 |
| A2 | 「`advanceUntil` 1s 步进必然在有限步内命中条件」 | **假**。步进期间任务可能整段未被调度（条件未成立），循环耗尽后**静默返回**，后续断言报出误导性文本。 |
| A3 | 「条件成立时精确计数断言必然成立」 | **假**。步进推进可能在观察到条件前多跨过一个节拍（过冲），使 `pollCycleCount == 1`、`planCardCount == 2` 这类断言把「调度允许的交错」当成必然。 |
| A4 | 「虚拟时钟推进即可，不必等定时器注册」 | **假**。定时器任务注册 `sleep` 是异步的（`Task{}` 内），推进可能发生在注册之前 → 等待者错过截止时刻。 |
| A5 | 「`cancel()` 后立即断言传输计数为 0」 | **假**（D16③ 已裁决：允许一次已授权的窗口调用）。必须用注入点把任务停在守卫之前，再放行并等**任务体退出**，否则断言既可能假绿（守卫未执行）也可能假红（窗口调用被算进去）。 |
| A6 | 「状态机写入发生在投递之前，所以拿到帧就等于状态已更新」 | **对**。`handle` 先写 `machine` 再 `apply` 投递，故「帧已到达」可作为状态机已更新的边界（用作多处等待依据）。 |
| A7 | 「轮询任务体结束（after 钩子）时 `receivePoll` 已完成」 | **对**。`receivePoll` 在任务体内 `await`，after 钩子在体末，故「after 信号」蕴含「结果已处理/已丢弃」。 |

## 四、冲突处理

- 无规格冲突；本任务是测试确定性修复，不改 D6 降级语义、不改 D16 有界取消语义。
- **冲突点**：`advanceUntil` 的注释曾自称「对注册空窗不敏感」——实测与之相反（它既受空窗影响，
  又会过冲）；按协调者裁决改为条件变量式推进，删除该函数。
- 上一轮未验证的 `git stash@{0}` 思路（信号原语 + 注入点）方向一致，但该 stash
  **删除了 1 个用例并把 `CORE_MIN` 下调到 370**——本实现**不采用**该部分：保数量、不降基线，
  被删用例改为确定性版本保留；其余实现独立重写并独立验证。

### 失败清单（本批复现到的原始输出）

```
OneStepStreamCoordinatorTests.swift:432: error: -[CovaCoreTests.OneStepStreamCoordinatorTests testCancelStopsSchedulingNewPollCycles] :
  XCTAssertEqual failed: ("0") is not equal to ("1") - 降级应恰好调度一个轮询周期
OneStepStreamCoordinatorTests.swift:439: error: -[CovaCoreTests.OneStepStreamCoordinatorTests testCancelStopsSchedulingNewPollCycles] :

```

命中 2 次的用例：`testCancelStopsSchedulingNewPollCycles`（同一次运行内两条断言连续报错，计 1 个失败用例）。

**机制（逐字对证假设 A2/A3）**：该用例用
`await advanceUntil(clock) { await coordinator.currentPhase() == .polling }` 等待降级——循环体是
「检查条件 → `advance(by: 1)` → 单次 `Task.yield()`」。高负载下定时器任务可能在 200 步内**一次都没被调度到**，
循环耗尽后**静默返回**；此时 `scheduledPollCycleCount()` 读到 0 → 断言 1 假红。随后（读计数与 `cancel()`
之间的窗口里）降级真正发生、周期计数变为 1 → 断言 2 又报「1 is not equal to 0」。
即：**失败文本不是 D16 语义被破坏，而是测试侧等待原语的静默放弃 + 过期读数**（这正是协调者裁决要根除的对象）。

## 七、测试侧确定性原语（新增/改造，全部在 `SSEStreamTestSupport.swift`）

| 原语 | 语义 | 取代 |
|---|---|---|
| `VirtualClock.advanceToNextDeadline(where:)` | 内部先等目标定时等待者**注册**（`sleep` 注册事件唤醒），再跳到其截止时刻并放行，返回放行数 | `assertEventually { pendingWaiterCount() > 0 }` + `advance(by: N)`；`advanceUntil` 1s 步进 |
| `GatedNowClock.armNowGate()` / `waitForBlockedNowCalls(_:)` | 拦住随后第 n 次 `now()`，事件化观测 | 「让出 N 次调度等它跑到」 |
| `AsyncGate`（多等待者化） | `reached.open()` + `release.wait()` 两段式 | `assertEventually { isWaiting() }` |
| `SignalCounter` | 注入点计数信号，`waitFor(n)` 事件驱动 | `Task.yield()` 轮询 |
| `FrameCollector.waitForCount/ waitForPlanCardCount/ planCardCount` | 帧数信号 | 轮询 `snapshot()` |
| `CompletionFlag.wait()` | 消费者退出信号 | `assertEventually { isCompleted() }` |
| `FakeSSEStreamingTransport.waitUntilTerminated()` | `onTermination` 信号 | `assertEventually { isTerminated() }` |
| `FakePlanPoller.waitForCalls(_:)` / `GatedPlanPoller.waitForCalls(_:)` | 轮询调用数信号 | `advanceUntil { callCount >= n }` |
| 删除 `advanceUntil` / `assertEventually` | 消除「未达条件静默返回」「有界让步断言」两类假绿/假红来源 | — |

## 八、生产代码最小改动（仅 `OneStepStream.swift`，TD-34 扩展）

1. 新增测试专用注入点 `setAfterSSETaskEnd` / `setAfterPollTaskEnd`（生产恒 nil）：给「任务体已退出」
   提供可等待边界。取消守卫的直接返回路径不产生任何其它可观测副作用，没有该信号就无法既**确定性**
   又**有杀伤力**地断言「守卫阻止了进入本轮周期」。
2. `performPoll` 的任务体由 `guard !Task.isCancelled else { return }` 改为
   `if !Task.isCancelled { ... }` + 体末 `await after?()`：**语义完全等价**（取消则跳过本轮），
   改动目的仅是让结束注入点在「被守卫提前返回」路径同样触发。
3. `startSSE` 体末 `await after?()`。
4. 生产默认 `nil` 时段落不产生额外挂起（可选闭包为空时不发生真正的挂起），行为与调用图语义不变。

**未改动**：D6 降级四个触发条件与阈值、SSE/轮询不并发、D16 有界取消语义、状态机纯逻辑。

## 十一、存疑点（不隐瞒）

1. **信号式等待的失败模式是挂起，而非快速失败**：若某次回归使「被等待事件」永不发生（例如定时器压根不再注册、
   周期不再调度），相关用例会挂起（`xcodebuild` 无默认测试超时），而不是立即报错。本轮变异点（V1–V4）特意选取
   「不移除被等待事件」的突变，均**快速变红**；但「事件永不发生」类回归的失败体验仍差。彻底消除需真实时间
   看门狗，或让门禁启用 `-test-timeouts-enabled`（会改动 `check.sh` 的测试调用方式，超出本轮授权）→ **建议**
   由协调者裁决是否登记为技术债（G4 前评估）。
2. **上游评审的完整失败清单（15 次 / 6 个用例 / 130000 执行）本轮未在本机完整复跑**：为把模拟器机时留给修复后
   验证，第 2 批复现跑到 28400 执行（3/26 用例）即中断，命中 1 个用例（2 条断言，见 §五）。其余 5 个用例的
   失败机制按上游报告 + 代码逐条对照推断，改造方案已覆盖全部 6 类机制（§六）。**未复现 ≠ 已验证**，如实记录。
3. `testDegradeIsIdempotentUnderConcurrentTickAndMalformedFrame` 的确定性构造依赖一个前提：`armNowGate()` 之后
   的**下一次** `now()` 调用来自目标坏事件帧的处理。该前提由「此刻只有 SSE 消费任务会调用 `now()`」（定时器
   在睡眠、尚无轮询任务）保证，已在源码注释写明；若未来协调器新增其它 `now()` 调用点，需重新评估。
4. `advanceToNextDeadline` 会一并放行「同一时刻已被取消但仍在册的旧定时器残影」（取消传播是异步的）。这些残影
   按同一时刻重判，不产生状态分叉（三坏事件/静默用例即含残影场景，已验证）；若未来状态机引入与时间无关的
   「唤醒次数」语义，需重新评估该放行策略。
5. `performPoll` 的 `guard` → `if` 是**语义等价改写**（取消即跳过本轮），仅为让结束注入点在「被守卫提前返回」
   路径触发；V2 变异（整段守卫移除 → 用例红）与全量门禁均已复核。生产恒 nil 时多出的 `await after?()` 不发生
   真挂起。
6. D16② 的「URLSession 层取消」仍以行为契约断言（`onTermination` 信号 / `.cancelled`），不观测 `stopLoading`
   ——沿用七审结论，本轮未改变。
7. `HANDOVER.md` 仍是未跟踪文件，内容停留在本修复之前（提到 `stash@{0}`、G3-d 未验收、旧 TD 列表）。本轮未改动
   该文件（不属本任务交付物）；协调者落证时应同步更新。`stash@{0}`（未验证的旧尝试）也保持原样未处置。
